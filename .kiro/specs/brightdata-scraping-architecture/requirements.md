# Requirements Document

## Introduction

This feature redesigns the Delta certification prep platform's scraping pipeline so that Bright Data Scraper Studio is the unmistakable core evidence-collection engine, not a convenience wrapper around Bing. The new architecture establishes a primary direct-doc-scraping path, a Bing-discovery fallback path, a Groq validation gate, a self-healing loop, and an explicit no-hallucination contract. Every piece of teaching content and every practice question must be grounded in data that Bright Data extracted — Groq reasons about facts; it does not invent them.

## Glossary

- **Scraper_Pipeline**: The end-to-end system that collects documentation content for an exam objective and produces validated structured data for downstream LLM consumption.
- **Bright_Data**: The Bright Data Scraper Studio service, accessed via the `@brightdata/cli` npx package, that creates, runs, heals, and caches web scrapers.
- **Collector**: A reusable Bright Data Scraper Studio scraper instance, identified by a `collector_id`, scoped to a `hostname + type` key and persisted in `.bdata-scrapers.json`.
- **Primary_Path**: The direct-scrape path where Bright Data scrapes a known official documentation URL without any Bing intermediary.
- **Fallback_Path**: The Bing-discovery path where Bright Data searches Bing to find a documentation URL, then scrapes that URL directly. Used only when no official URL is resolvable.
- **Official_URL**: The authoritative documentation URL for an objective, resolved from (in priority order): the objective's skill entries in the blueprint JSON, derivation from cert provider + objective title, or discovery via the Fallback_Path.
- **Source_Confidence**: An internal classification of how a documentation URL was obtained. Values: `official_blueprint` (URL came directly from `official_doc_url` in Blueprint_JSON), `provider_derived` (URL was constructed from provider mapping), `fallback_discovered` (URL was discovered via Bing Fallback_Path). This classification affects the UI label shown to learners.
- **Extraction_Validation_Gate**: Deterministic TypeScript validation of Bright Data's extraction output. Groq is used downstream for teaching generation and, where appropriate, scraper-healing instructions. This is NOT a Groq LLM call.
- **Heal_Loop**: A single cycle of `scraper heal → scraper approve → scraper run` triggered when the Extraction_Validation_Gate marks an extraction as invalid.
- **Extraction_Result**: The structured JSON object that Bright Data produces for a documentation page, containing the fields: `title`, `learning_outcomes`, `key_concepts`, `api_names`, `limits`, `code_examples`.
- **Scrape_Status**: A metadata object attached to every scrape attempt, recording the path taken (`primary` | `fallback`), whether healing occurred, and the final outcome (`valid` | `invalid` | `failed`). Also includes `source_confidence: 'official_blueprint' | 'provider_derived' | 'fallback_discovered'` for UI display.
- **Teach_Content**: The teaching explanation object generated by Groq for a given objective, grounded exclusively in a valid Extraction_Result.
- **Heal_Badge**: A visible UI indicator rendered when the Heal_Loop was triggered during a scrape, e.g. `[~] scraper healed — missing learning outcomes recovered`.
- **Failure_State**: The explicit error response returned when the Scraper_Pipeline cannot produce a valid Extraction_Result at any point in the pipeline — including URL resolution failure, Fallback_Path invocation failure, or failed validation after the Heal_Loop. No LLM-generated fallback content is permitted.
- **Blueprint_JSON**: One of the JSON files in `data/blueprints/` that defines objectives and skills. Each skill entry may carry an `official_doc_url` field.
- **Official_Domains**: The set of hostnames treated as authoritative documentation sources: `learn.microsoft.com`, `docs.microsoft.com`, `docs.aws.amazon.com`, `cloud.google.com`, `docs.azure.com`, `docs.databricks.com`, `docs.snowflake.com`, `docs.oracle.com`, `developer.hashicorp.com`, `kubernetes.io`, `docs.docker.com`, `docs.github.com`, `developer.salesforce.com`, `docs.confluent.io`, `docs.redhat.com`.
- **Scrapers_Cache**: The `.bdata-scrapers.json` file at the project root that maps `hostname → type → collector_id`.
- **Teach_Route**: The Next.js route at `app/api/objectives/[id]/teach/route.ts`.
- **Update_Route**: The Next.js route at `app/api/certifications/[id]/update/route.ts`.

## Requirements

### Requirement 1: Primary Direct-Doc Scraping Path

**User Story:** As the platform, I want to scrape official documentation pages directly for each exam objective, so that Bright Data is demonstrably the evidence collector and the pipeline is not reducible to a Bing API call.

#### Acceptance Criteria

1. WHEN the Scraper_Pipeline is invoked for an objective, THE Scraper_Pipeline SHALL attempt the Primary_Path first by resolving an Official_URL before attempting the Fallback_Path.
2. WHEN resolving an Official_URL, THE Scraper_Pipeline SHALL inspect the objective's skill entries in the Blueprint_JSON and use the first `official_doc_url` value found whose hostname is in Official_Domains.
3. IF no `official_doc_url` is present in the objective's skills, THEN THE Scraper_Pipeline SHALL attempt to derive an Official_URL by constructing a known pattern URL from the cert provider, objective title, and a static domain mapping (e.g. Microsoft → `learn.microsoft.com`, AWS → `docs.aws.amazon.com`, GCP → `cloud.google.com`).
4. WHEN a valid Official_URL has been resolved, THE Scraper_Pipeline SHALL invoke Bright_Data to scrape that URL directly without performing a Bing search.
5. THE Scraper_Pipeline SHALL record `path: "primary"` in the Scrape_Status when the Primary_Path is used, and SHALL retain this value through all Primary_Path operations even if the Fallback_Path is subsequently invoked.
6. WHEN the Scraper_Pipeline resolves an Official_URL, THE Scraper_Pipeline SHALL record the Source_Confidence in the ScrapeStatus as `official_blueprint` if the URL came from Blueprint_JSON, `provider_derived` if it was constructed by `deriveUrlFromProvider`, or `fallback_discovered` if it was found via the Fallback_Path.

---

### Requirement 2: Bing Fallback as URL Discovery Only

**User Story:** As the platform, I want to use Bing search exclusively as a URL-discovery step when no Official_URL is known, so that Bing is never the primary evidence source.

#### Acceptance Criteria

1. WHEN the Primary_Path cannot resolve an Official_URL for an objective — meaning both the Blueprint_JSON lookup (criterion 1.2) and the pattern derivation (criterion 1.3) have been attempted and neither yielded a valid Official_URL — THE Scraper_Pipeline SHALL invoke the Fallback_Path using the existing Bing Collector (`c_mt10dg5i258f47a685` for `www.bing.com → documentation_search`).
2. WHEN the Fallback_Path runs, THE Scraper_Pipeline SHALL submit a Bing search query and extract the top result URL whose hostname is in Official_Domains.
3. WHEN the Fallback_Path has identified a documentation URL, THE Scraper_Pipeline SHALL scrape that URL directly with Bright_Data rather than using the Bing snippet text as evidence.
4. IF the Fallback_Path cannot identify any URL in Official_Domains from the Bing results, THEN THE Scraper_Pipeline SHALL record a Failure_State with reason `"no_official_url_found"`.
5. THE Scraper_Pipeline SHALL record `path: "fallback"` in the Scrape_Status when the Fallback_Path is used.
6. IF the Fallback_Path invocation itself fails (e.g., the Bing Collector call returns an error), THEN THE Scraper_Pipeline SHALL record a Failure_State with reason `"fallback_invocation_failed"`.

### Requirement 3: Structured Extraction Schema

**User Story:** As a downstream Groq consumer, I want Bright Data to produce a consistent structured object with defined fields, so that validation is deterministic and hallucination is detectable.

#### Acceptance Criteria

1. WHEN Bright_Data scrapes a documentation page, THE Scraper_Pipeline SHALL instruct the Collector to extract a JSON object containing the fields: `title` (string), `learning_outcomes` (array of strings), `key_concepts` (array of `{term, definition}` objects), `api_names` (array of strings), `limits` (array of strings), `code_examples` (array of strings).
2. THE Scraper_Pipeline SHALL pass this structured extraction prompt to `scraper create` when creating a new Collector for a documentation hostname.
3. WHEN the Collector already exists in the Scrapers_Cache for a given `hostname → doc_content` key, THE Scraper_Pipeline SHALL reuse that Collector without creating a new one.
4. THE Scraper_Pipeline SHALL attempt to persist a new Collector ID to the Scrapers_Cache immediately after a successful `scraper create` call; if the Scrapers_Cache write fails, THE Scraper_Pipeline SHALL log the error and continue the scrape operation without treating the cache write failure as a pipeline error.

---

### Requirement 4: Extraction Validation Gate

**User Story:** As the no-hallucination contract enforcer, I want to validate Bright Data's extraction before any teaching content is generated, so that content generation never reasons from absent or boilerplate data.

#### Acceptance Criteria

1. WHEN Bright_Data returns an Extraction_Result, THE Extraction_Validation_Gate SHALL evaluate whether the `title` field is non-empty and the `key_concepts` array contains at least one entry with a non-empty `term` and `definition`.
2. WHEN the Extraction_Validation_Gate determines the Extraction_Result is valid, THE Scraper_Pipeline SHALL mark the Scrape_Status as `outcome: "valid"`.
3. WHEN the Extraction_Validation_Gate determines the Extraction_Result is invalid, THE Extraction_Validation_Gate SHALL return a `missing_fields` string describing what is absent or inadequate, and THE Scraper_Pipeline SHALL trigger the Heal_Loop.
4. THE Extraction_Validation_Gate SHALL NOT generate or supplement content — its sole output SHALL be `{ "is_valid": boolean, "missing_fields": string }`.
5. WHEN the Scrape_Status is marked `outcome: "valid"`, THE Teach_Route SHALL proceed to Teach_Content generation.

---

### Requirement 5: Self-Healing Loop

**User Story:** As the platform, I want the pipeline to attempt one automatic heal cycle when Bright Data returns incomplete data, so that transient extraction failures are recovered without human intervention.

#### Acceptance Criteria

1. WHEN the Heal_Loop is triggered, THE Scraper_Pipeline SHALL call `scraper heal` on the Collector with a prompt that names the missing fields identified by the Extraction_Validation_Gate.
2. WHEN `scraper heal` succeeds, THE Scraper_Pipeline SHALL call `scraper approve` on the same Collector before re-running it.
3. WHEN the healed Collector has been approved, THE Scraper_Pipeline SHALL call `scraper run` once more and submit the result to the Extraction_Validation_Gate for a second validation pass.
4. THE Scraper_Pipeline SHALL execute the Heal_Loop at most once per scrape invocation — recursive healing is not permitted.
5. WHEN the second validation pass returns `is_valid: true`, THE Scraper_Pipeline SHALL record `healed: true` in the Scrape_Status, independently of whether Teach_Content generation subsequently proceeds; Teach_Content generation may still be blocked by external signals.
6. IF the second validation pass returns `is_valid: false`, THEN THE Scraper_Pipeline SHALL record a Failure_State and SHALL NOT proceed to Teach_Content generation.

---

### Requirement 6: No-Hallucination Contract

**User Story:** As a learner preparing for a certification exam, I want the platform to return a clear failure rather than fabricated content when documentation cannot be retrieved, so that I am never misled by invented facts.

#### Acceptance Criteria

1. IF the Scraper_Pipeline records a Failure_State for any reason, THEN the Teach_Route SHALL return an HTTP 422 response with `{ "success": false, "error": "extraction_failed", "reason": "<Failure_State reason>" }` rather than generating Teach_Content.
2. THE Teach_Route SHALL NOT invoke any content generation when the Scrape_Status outcome is `"failed"`.
3. THE Teach_Route SHALL NOT use the `buildFallbackTeachContent` function as a silent substitute when Bright Data extraction fails.
4. WHEN a Failure_State is returned to the client, THE Teach_Route SHALL include a `scrape_status` field in the response body so the UI can display a meaningful error to the learner.
5. WHERE Groq is not configured, THE Scraper_Pipeline SHALL still run and persist valid Extraction_Results; Teach_Content generation is skipped but the scrape is not considered failed.

---

### Requirement 7: Scrape Status Propagation to UI

**User Story:** As a learner, I want to see when the scraper healed or when content came from a fallback path, so that I trust the transparency of the platform's evidence collection.

#### Acceptance Criteria

1. WHEN the Scrape_Status `healed` field is `true`, THE Teach_Route SHALL include a `heal_badge` field in the response with a human-readable message in the format `"[~] scraper healed — missing <field_names> recovered"`.
2. WHEN the Scrape_Status `path` field is `"fallback"`, THE Teach_Route SHALL include a `source_note` field indicating that a Bing URL discovery step was used.
3. WHEN presenting source information to a learner, THE Teach_Route SHALL translate Source_Confidence values to human-readable labels: `official_blueprint` → "Official source", `provider_derived` → "Official-domain source discovered automatically", `fallback_discovered` → "Official-domain source discovered via search". Technical pipeline details (collectorId, scrapeMethod, path field) SHALL be available only through progressive disclosure (e.g. a "View source & extraction details" expandable section) and SHALL NOT appear in the primary learner-facing response.
4. WHEN the Teach_Route returns a successful Teach_Content response, THE response SHALL include a `scrape_status` object containing at minimum the fields: `path`, `healed`, `outcome`, and `source_url`; IF any of these required fields are unavailable and the `scrape_status` object cannot be fully assembled, THEN THE Teach_Route SHALL return a failure response with reason `"missing_scrape_metadata"` rather than returning a partial or absent `scrape_status`.
5. THE Update_Route SHALL include the `scrape_status` in each `objective_done` NDJSON event it emits, so the bulk-update UI can display per-objective scrape metadata.

---

### Requirement 8: Scraper Caching and Reuse

**User Story:** As an operator, I want scrapers to be created once per hostname and reused on every subsequent call, so that Bright Data API costs do not scale with the number of scrape invocations.

#### Acceptance Criteria

1. THE Scraper_Pipeline SHALL look up `hostname → "doc_content"` in the Scrapers_Cache before calling `scraper create` for any documentation page.
2. WHEN a Collector ID is found in the Scrapers_Cache, THE Scraper_Pipeline SHALL call `scraper run` directly without calling `scraper create`.
3. THE Scrapers_Cache SHALL preserve the existing `www.bing.com → documentation_search → c_mt10dg5i258f47a685` entry and SHALL NOT overwrite it.
4. WHEN a new Collector is created by the Scraper_Pipeline, THE Scraper_Pipeline SHALL attempt to write the new `hostname → "doc_content" → collector_id` entry to the Scrapers_Cache before running the scraper; if the Scrapers_Cache write fails, THE Scraper_Pipeline SHALL proceed to run the scraper, accepting that a duplicate Collector may be created on future calls for the same hostname.

### Requirement 9: Teach Content Grounded in Extraction Result

**User Story:** As an instructor designing teaching content, I want Groq to receive only the validated Extraction_Result as its factual input, so that every claim in the generated teaching material can be traced back to a real documentation source.

#### Acceptance Criteria

1. WHEN `generateTeachContent` is called, THE Teach_Route SHALL pass the validated Extraction_Result fields (`learning_outcomes`, `key_concepts`, `api_names`, `limits`, `code_examples`) as the primary factual context in the Groq prompt.
2. THE Groq prompt for Teach_Content generation SHALL explicitly instruct the model to derive facts only from the provided Extraction_Result and to avoid adding details not present in the source data.
3. WHEN the Extraction_Result does not contain a value for a specific field (e.g., `limits` is an empty array), THE Teach_Route SHALL pass `null` for that field rather than omitting it, so the prompt communicates explicit absence rather than unknown state.
4. THE generated Teach_Content response SHALL include a `sources_used` field set to `"Bright Data Scraper Studio — <source_url>"` when built from a valid Extraction_Result.
5. THE Teach_Route SHALL NOT call `generateTeachContent` when the Extraction_Validation_Gate has returned `is_valid: false` for the current Extraction_Result.

---

### Requirement 10: Bulk Update Route Compatibility

**User Story:** As an operator running a bulk certification update, I want the new pipeline to work within the existing streaming NDJSON update route without breaking concurrency or error handling, so that bulk scraping continues to work at scale.

#### Acceptance Criteria

1. WHEN the Update_Route invokes the Scraper_Pipeline for an objective, THE Scraper_Pipeline SHALL return a result object that includes `scrape_status`, `combinedContent`, `sources`, and `scrapeMethod` fields compatible with the existing `saveScrapedSource` call signature.
2. WHEN the Scraper_Pipeline returns a Failure_State for an objective during bulk update, THE Update_Route SHALL emit an `objective_error` NDJSON event (not `objective_done`) and SHALL continue processing remaining objectives; THE Update_Route SHALL NOT emit both `objective_done` and `objective_error` for the same objective.
3. WHEN the Scraper_Pipeline returns a healed result, THE Update_Route SHALL emit an `objective_done` event whose `message` field contains the Heal_Badge string.
4. THE Update_Route SHALL NOT increase its NDJSON event types beyond the existing set: `start`, `progress`, `objective_done`, `objective_warn`, `objective_error`, `done`.

---

### Requirement 11: Learner-Facing Error Translation

**User Story:** As a learner, I want to see a clear, human-readable explanation when content cannot be loaded, so that I understand what happened without needing to debug the platform's infrastructure.

#### Acceptance Criteria

1. WHEN the Teach_Route returns a Failure_State response, THE response SHALL include a `user_message` field containing a plain-English description of the problem, in addition to the technical `reason` field.
2. THE following translation map SHALL be applied: `no_official_url_found` → "We couldn't find official documentation for this topic right now.", `fallback_invocation_failed` → "We couldn't reach the documentation source right now. Please try again.", `validation_failed_after_heal` → "We found the source but couldn't extract the required information, even after an automatic repair attempt.", `scraper_run_failed` → "We couldn't retrieve the documentation page right now. Please try again.", `missing_scrape_metadata` → "An internal error occurred while verifying the source. Please try again."
3. IF the `scrape_status.healed` field is `true` and `outcome` is `"failed"`, THEN the `user_message` SHALL acknowledge the automatic repair attempt: "We found the source but couldn't extract the required information, even after an automatic repair attempt."
4. THE `reason` field (technical failure code) SHALL remain present in the response for logging and debugging, but SHALL be clearly separated from the `user_message` field in the response body.

---

### Requirement 12: Practice and Retrieval Loop

**User Story:** As a learner preparing for a certification exam, I want the platform to check my understanding after each lesson and give me targeted practice questions, so that I actively retain the material rather than passively reading it.

#### Acceptance Criteria

1. WHEN a learner has received a Teach_Content response for an objective, THE platform SHALL offer a "Check my understanding" action that generates a practice question grounded in the same validated Extraction_Result used to produce the Teach_Content.
2. WHEN a practice question is generated, THE practice question SHALL be derived only from the Extraction_Result's `key_concepts`, `learning_outcomes`, and `exam_tip` fields — it SHALL NOT introduce concepts absent from the validated source material.
3. WHEN a learner submits an answer to a practice question, THE platform SHALL return feedback that explains whether the answer is correct, and if incorrect, SHALL explain why using only facts present in the Extraction_Result.
4. WHEN a learner answers a practice question incorrectly, THE platform SHALL record the objective as a weak topic for that learner session.
5. WHEN weak topics are recorded for a learner, THE platform SHALL offer a targeted reteach action that re-presents the Teach_Content for those objectives, emphasising the `common_mistakes` and `exam_tip` fields.
6. THE practice question and feedback generation SHALL follow the same no-hallucination contract as Teach_Content: if the Extraction_Result is not valid (`outcome !== "valid"`), practice questions SHALL NOT be generated and THE platform SHALL return HTTP 422.
